### ⚠️ 两个必须记住的坑

1. **`01_increment.sql` 会因行格式报 `Row size too large 8126`**
   db-data 建表带 `ROW_FORMAT=Compact`（12 张表），先批量转 `DYNAMIC` 再跑 01。
2. **QRTZ 表不能用 `TRUNCATE` 全清**

   admin 启动即炸 `Couldn't retrieve trigger: TASK_19`。
   正确顺序：先删子表（triggers/cron/simple/fired 等）→ 再 `DELETE FROM qrtz_job_details` → 计数确认全 0 → 启动，程序会从 `eb_schedule_job` 自动重建 21 个任务。

## 五、SSL 证书 & 宝塔面板站点注册

### 5.1 为什么面板「网站」列表一开始看不到 → 已修复

宝塔 8.x 的站点列表存在 **`/www/server/panel/data/db/site.db`**（**不是** `default.db`），
分 `sites`（站点）与 `domain`（域名绑定）两张表。

部署时 vhost 是手工写入的、没走面板流程，所以面板列表里没有它们（但 nginx 一直正常加载）。
现已补注册：

| sites.id | 域名 | 目录 |
|---|---|---|
| 11 | adminqf.qianxutec.com | `/www/wwwroot/adminqf.qianxutec.com` |
| 12 | apiqf.qianxutec.com | `/www/wwwroot/apiqf.qianxutec.com` |
| 13 | appqf.qianxutec.com | `/www/wwwroot/appqf.qianxutec.com` |

⚠️ 三个坑：
1. **`index` 是 SQLite 保留字**，INSERT 时必须写成 `"index"`，否则整条语句失败（且不报事务错误）。
2. INSERT 失败时后续语句仍会执行 → `domain` 表会残留 `pid` 指向不存在站点的孤儿行，收尾要 `DELETE FROM domain WHERE pid NOT IN (SELECT id FROM sites)`。
3. 改完要 `/etc/init.d/bt restart` 面板才会重新读库。
4. 面板注册**只影响面板显示**，不重写 nginx 配置 —— 所以反代规则不会丢。
5. 备份：`/www/server/panel/data/db/site.db.bak-qifu-*`

### 5.2 SSL 已签发（走 acme.sh，不走面板一键）

选 acme.sh 的原因：面板「一键 SSL」会重写 vhost 文件，而本套 vhost 的 location 顺序是精心排的
（`^~ /.well-known/` → `/api/public/safety/` → `/api/(front|public)/` → `/`），一旦被覆盖就全乱。

```bash
# 安装（gitee 镜像）
git clone --depth 1 https://gitee.com/neilpang/acme.sh.git /tmp/acme_src
cd /tmp/acme_src && ./acme.sh --install -m admin@qianxutec.com
acme.sh --set-default-ca --server letsencrypt     # 默认 ZeroSSL，切成 LE

# 签发（webroot 模式，三域名各一张）
acme.sh --issue -d <域名> --webroot /www/wwwroot/acme-challenge

# 安装到宝塔标准路径 + 续期后自动 reload
acme.sh --install-cert -d <域名> --ecc \
  --key-file       /www/server/panel/vhost/cert/<域名>/privkey.pem \
  --fullchain-file /www/server/panel/vhost/cert/<域名>/fullchain.pem \
  --reloadcmd      "nginx -s reload"
```

配套改动：
1. 建 webroot：`/www/wwwroot/acme-challenge/.well-known/acme-challenge`（`www:www` / `755`）
2. 三个 vhost 各加一段 —— **必须是 `^~` 前缀匹配**，否则 apiqf 的 `location ~ ^/api/...`
   正则会先命中，把 ACME 校验请求反代给 Java 服务，验证必然失败：
   ```nginx
   location ^~ /.well-known/acme-challenge/ {
       root /www/wwwroot/acme-challenge;
       default_type text/plain;
       access_log off;
   }
   ```
3. 在 `listen 80;` 后插入 `listen 443 ssl;` + `http2 on;` + 证书路径
4. 自动续期 cron 由 acme.sh 自动添加（每天 1/7/13/19 点检查）

证书类型 **ECC（ECDSA P-256）**，签发者 Let's Encrypt，有效期至 **2026-12-31**。
（2026 年 ECC 兼容无问题：Android 4.0+ / iOS 5+ 全支持，且比 RSA 更快更小。）


> ⚠️ **node 版本**：本项目 vue-cli 4 + webpack 4，**node 17 及以上**才需要
> `NODE_OPTIONS=--openssl-legacy-provider`；node ≤16 **不能加**（会报
> `xxx is not allowed in NODE_OPTIONS`，构建直接失败 —— 2026-10-03 实测）。
> `build-admin.sh` 已按 `node -v` 自动判断，无需手工处理。

**③ nginx 80 → 443 跳转**

```nginx
set $qf_redirect "";
if ($scheme = http) { set $qf_redirect "1"; }
if ($request_uri ~ ^/\.well-known/acme-challenge/) { set $qf_redirect ""; }
if ($qf_redirect = "1") { return 301 https://$host$request_uri; }
```

⚠️ **两个坑，缺一个都出事**：

1. **必须限定 `$scheme = http`**。因为宝塔风格的 vhost 把 `listen 80` 和 `listen 443 ssl`
   写在**同一个 server 块**里，server 级 `if` 对两个端口都生效 —— 不加这个条件，
   https 请求会被 301 到自己，形成**死循环**（表现：https 返回 301 而不是 200）。
2. **必须放行 `/.well-known/acme-challenge/`**。否则续期时：证书已过期 → LE 走 http 验证 →
   被 301 到 https → https 证书无效 → 验证失败 → **续期永远失败**，死锁。

> 排查手法：`curl -s -o /dev/null -w "%{http_code}->%{redirect_url}" http://域名/` 与
> `curl -s -o /dev/null -w "%{http_code}" https://域名/` 对照着看。

**④ 清 Redis 配置缓存**：`redis-cli -n 12 DEL config_list`（admin/front 已共用 db12），
然后重启 Java 服务。原来 admin 用的 db11 已废弃，只需在首次切换时 `DEL` 一次即可。

## 六、⚠️ 后台改「服务设置」前台不生效 —— admin/front 必须共用同一个 Redis 库

> 2026-10-02 16:15 修复。用户报：「企业管理里面的服务设置，我设置首页和会员中心都没有生效」。

### 6.1 现象

后台「大市场 → 企业管理 → 服务设置」把「软件开发首页设为商城主页」「软件开发会员中心」打开后：

- 数据库 `eb_system_config` 里 `svc_home_mode=1`、`svc_user_mode=1` —— **值确实写进去了**
- 会员端接口 `/api/front/svc/config` 却一直返回 `homeMode:false`、`userMode:false`
- 同一个方法读的 `navMode` / `signSms` 反而正常 `true`（这个细节最迷惑人）

### 6.2 根因：两个 jar 的 `asyncConfig` 是**故意不同**的

| jar | `qianxu.asyncConfig`（prod） | 含义 |
|---|---|---|
| `Qianxu-admin.jar` | **`false`** | 后台读配置**直查 MySQL**（改完自己立刻看到） |
| `Qianxu-front.jar` | **`true`** | 会员端读配置**走 Redis `config_list` 缓存**（省 DB） |

这是源码原生设计。为了补「后台改了、会员端缓存不刷新」这个洞，
`SystemConfigServiceImpl.updateOrSaveValueByName()` 在保存成功后会**强制 `hset` 一次 Redis**，
代码注释原文：

> `// admin 常关 asyncConfig、front 常开：后台改配置若只写库不刷 Redis，会员端会一直读到旧值`
> `// 因此保存成功后始终刷新 Redis 中对应项（Redis 不可用时不影响落库结果）`

**但这个补洞的前提是：admin 和 front 连同一个 Redis 库。**

本次部署为了「三重隔离」，我把 admin 放 db11、front 放 db12 ——
于是后台刷新的是 **db11**，front 读的是 **db12**，**永远刷不到**。

更糟的是它**不会自愈**：

```java
// loadingConfigCache()：只在 hash 为空时才全量加载
if (hashSize > 0) { return; }
// get()：命中缓存就直接返回，不比对 DB
Object data = redisUtil.hget(Constants.CONFIG_LIST, name);
if (ObjectUtil.isNotNull(data)) { return data.toString(); }
```

所以每次改配置都会复现，是**架构级**问题，不是偶发故障。

**对照主项目**（api.qianxutec.com）为什么没事：它的 admin 和 front 都没指定 `--spring.redis.database`，
统一用 jar 内 prod 的 `database: 8` —— **两端本来就共用一个库**。我这次是「隔离过度」了。

### 6.3 修复

让 admin 与 front 共用同一个库（`qifu-service.sh` 内）：

```bash
start_one admin 21800 "$ADMIN_JAR" --spring.redis.database=12 --spring.redis.second.database=14
start_one front 21810 "$FRONT_JAR" --spring.redis.database=12 --spring.redis.second.database=14
```

改完**必须清一次脏缓存**再启动 —— 否则 front 先起来发现 hash 非空会跳过全量加载，脏值继续留着：

```bash
cd /www/wwwroot/apiqf.qianxutec.com
./qifu-service.sh stop
redis-cli -a <pwd> -n 12 DEL config_list     # 清脏缓存
redis-cli -a <pwd> -n 11 DEL config_list     # 清旧库残留（db11 已废弃）
./qifu-service.sh start                       # 等 20~25s
```

### 6.4 验证（闭环，必须做）

```bash
# ① 会员端接口应返回 true
curl -s .../api/front/svc/config
→ {"homeMode":true,"userMode":true,"navMode":true,...}   ✅

# ② 后台改一次 → 会员端必须立刻跟着变（这才是闭环）
T=<admin token>
curl -s -X POST .../api/admin/svc/setting/save -H "Authori-zation: $T" -d '{"svc_nav_mode":"0"}'
curl -s .../api/front/svc/config     → navMode:false   ✅ 立即同步
# 验证完记得改回 "1"
```

### 6.5 以后遇到「后台改了前台没变」的三步排查法

1. **先看库**：`SELECT name,value FROM eb_system_config WHERE name='xxx'` —— 值到底进没进库
2. **再验 front 读的是哪个库**：往怀疑的库写个假值 `HSET config_list xxx ZZTEST`，
   若接口**立刻报 JSON 解析错**（`Unrecognized token 'ZZTEST'`），说明它读的**就是这个库**
   （这一招比看连接数可靠，也是本次定位成功的关键一步）
3. **最后比两个 jar 的 `spring.redis.database`** 是否相同 —— 不同就必须统一

## 四、本次执行的部署步骤（可复现）

1. **克隆**：`git clone git@gitee.com:qianxutec/qianxuqifu.git /Users/qianxu/WorkBuddy/qianxuqifu/repo`
2. **建库导数**（MySQL 8.0 @3306，root/root）：
   ```bash
   mysql -uroot -proot --default-character-set=utf8mb4 --max_allowed_packet=512M < qianxu/sql/00_full_install.sql
   mysql -uroot -proot --default-character-set=utf8mb4 qianxu_java3 < qianxu/sql/01_increment.sql
   mysql -uroot -proot --max_allowed_packet=512M qianxu_java3 < db-data/qianxu_full_data_export.sql
   ```
3. **合并图片**：`cp -Rn db-data/qianxu_image/qianxuimage/. qianxu/qianxuimage/`
4. **打包**：`cd qianxu && JAVA_HOME=~/.jdks/zulu8... ./mvnw -DskipTests clean package`（BUILD SUCCESS）
5. **修 Quartz BLOB**：00_full_install.sql 里的 QRTZ 调度表 BLOB 在导出时被转码损坏
   （`StreamCorruptedException: invalid stream header: EFBFBDEF`），已 TRUNCATE 全部 QRTZ 表
   —— 程序启动时 `ScheduleJobServiceImpl.init()` 会从 `eb_schedule_job` 自动重建，无需手工干预。
6. **启动后端**（关键启动参数，均在命令行覆盖，不改源码）：
   ```bash
   java -jar qianxu/qianxu-admin/target/Qianxu-admin.jar \
     --server.port=18080 \
     --spring.datasource.url='jdbc:mysql://127.0.0.1:3306/qianxu_java3?characterEncoding=utf-8&useSSL=false&serverTimezone=Asia/Shanghai&allowPublicKeyRetrieval=true' \
     --spring.datasource.password=root \
     --qianxu.imagePath=/Users/qianxu/WorkBuddy/qianxuqifu/repo/qianxu/ \
     --spring.redis.database=12 --spring.redis.second.database=9
   # front 同理：--server.port=18081 --spring.redis.database=12 --spring.redis.second.database=9
   # ⚠ 两端的 database 必须相同 —— 原因见文末「Redis 库号修正」
   # 现已封装成脚本，日常不用再手敲：bash deploy-182/local-service.sh {start|stop|restart|status}
   ```
7. **启动管理前端**：
   ```bash
   export PATH="$HOME/.nvm/versions/node/v16.20.2/bin:$PATH"
   unset NODE_OPTIONS   # ⚠️ 必清，WorkBuddy 注入的 safe-delete shim 会拦 webpack
   cd admin && port=19527 node node_modules/@vue/cli-service/bin/vue-cli-service.js serve
   ```

## ⚠️ Redis 库号（两次修正，2026-10-02）

### 修正一（14:35）：库号越界 → 连接静默失败

初版用 db22/23/24/25 想隔离主项目，但这台 Redis 是默认配置**只有 16 个库（db0–15）**，
越界后 Jedis 连接全部失败，而 `RedisUtil` 把异常吞掉（printStackTrace + return false），
应用表面正常、验证码/Token 全部静默失效 → 登录页报「验证码已过期」。

> 教训：凡是「连接型依赖的异常被吞掉」的设计，出问题**先怀疑连接**，别只盯业务日志。

### 修正二（16:35）：admin / front 必须共用同一库

原先是 admin 用 db11、front 用 db12 —— 这正是**线上那个坑的本地版**。

根因：prod profile 下 **front 的 `asyncConfig=true`（读 Redis 缓存）**、
**admin 的 `false`（直查库）**，靠「后台保存时强制刷 Redis」来补
「会员端缓存不更新」这个洞；**两端分成两个库，补洞就被切断** ——
表现为后台改配置、会员端永远读旧值，而且**不报任何错**。

现已对齐为**共用**（与线上 182 的 db12 同构）：

| | 业务库 | 微信库 |
|---|---|---|
| admin | **db12** | **db9** |
| front | **db12** | **db9** |

避开的库：本机主项目 tech.qianxu 占 db10 / db13 / db14。

> 本地服务跑的是 base profile（`asyncConfig: false`），两端都直查库，
> 所以本地**没暴露**这个现象；但参数已对齐，将来切 prod 也不会踩。
>
> 已实测闭环：后台存 `svc_nav_mode=0` → 会员端**立即** `navMode:false`；改回 `1` 同步 ✅
